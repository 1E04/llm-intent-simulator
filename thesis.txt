1.1

motivation

Companies are increasingly using virtual assistants in chat or telephony
systems. In doing so, businesses see significant potential for cost savings,
as customer requests can either be fully resolved by virtual assistants or
the average call duration with a human agent can be reduced through prequalification by the assistant. However, this savings potential critically depends on virtual assistants reliably understanding users’ natural language
phrasing. In practice, requests are expressed in widely varying ways (e.g.,
indirectly, imprecisely, colloquially, or with differing communication styles),
and it is precisely this variance that poses a central challenge for intent recognition by virtual assistants. In the development of virtual assistants, techniques from Natural Language Understanding (NLU) or optimized prompting when using LLM are used to make the quality of intent recognition robust against the variance and diversity of potential phrasings. Quality assurance for this capability is often conducted through manual testing, which
provides qualitative results but is fundamentally time- and labor-intensive,
making it poorly scalable and insufficiently reproducible. As a result, many
test setups fail to adequately cover the diversity of natural language phrasing and communicative differences across user groups. Furthermore, natural
language inherently allows room for interpretation and ambiguity. This combination of interpretive leeway and inadequate test coverage complicates a
robust evaluation of intent recognition.
1.2

research objectives

Against this background, the planned work aims to design and evaluate a
framework for automated testing of virtual assistant intent recognition. In
doing so, it investigates the extent to which LLM can be used as user simulators to generate different customer types and varying expressions in a
targeted and controlled manner. In this way, the robustness of intent classification against linguistic variance is to be systematically tested. Building
on this, the study examines whether an LLM acting as an LLM-as-a-Judge is
suitable for validly assessing both the generated linguistic diversity and the
virtual assistant’s handling of room for interpretation. The primary research
interest lies in determining the extent to which such an approach not only
reveals weaknesses in intent recognition, but also provides insights into pos-

BACKGROUND

2.1

conversational ai & dialog systems

A dialogue system in the context of a contact center is a framework that enables communication between customers and the organization. Communication can occur through two primary channels: text-based (chat) and voicebased interactions. Dialogue systems process user input received through
chat or voice, interpret the user’s intent, generate appropriate responses,
and, when necessary, execute specific actions or requests.
The implementation of a dialogue system requires several interconnected
components. For voice-based communication, an Automatic Speech Recognition (ASR) module converts spoken language into textual input. Subsequently, an Intent Recognition System analyzes the input and determines
the user’s intent. Depending on the identified intent, the system may either
retrieve a predefined response or utilize a language model to generate a
contextually appropriate reply. In scenarios where the intent triggers the execution of a specific task, an authentication mechanism is typically required
to ensure secure access. The requested operation is then performed through
Application Programming Interface (API) or other system-level functions.
2.1.1

Chatbots vs. Voicebots (ASR & TTS Pipelines)

Dialogue systems are broadly categorized by their interaction medium:
chatbots: A chatbot receives text input from a user and generates a text
response. Traditional rule-based chatbots rely on keyword matching or hardcoded decision logic. Modern LLM-based chatbots leverage deep learning to
generate responses dynamically token by token [1, 2].
voicebots: A voicebot acts as a multimodal layer built on top of a dialogue management system to process speech input and output. The pipeline
utilizes ASR (also referred to as Speech-to-Text (STT)) to convert spoken audio
into a text transcription. After the central dialogue system processes the text,
the response is delivered back to the user as audio using Text to Speech (TTS)
synthesis or pre-recorded audio snippets [1, 2].
2.1.2

Natural Language Understanding & Intent Recognition

Within goal-oriented dialogue systems, intent recognition (or intent classification) is the fundamental NLU task of identifying a user’s primary goal.
Instead of relying on isolated keywords or the explicit surface text of a mes-

sage, this process evaluates the holistic semantic meaning of the entire sentence. It then translates this unstructured natural language into a specific
label that enables the system to execute the appropriate next-turn action. [3,

2.1.3

Evaluation Metrics for NLU

Evaluating NLU goes beyond simple classification. To accurately assess a system’s performance, it is crucial to distinguish between single-turn and multiturn interactions. Single-turn classification assumes that each user query is
isolated and contains all necessary information to deduce the intent [5]. Conversely, multi-turn interactions span across several exchanges, requiring the
system to track the conversational context and dialogue history to correctly
interpret the user’s current goal [6, 7].
Intent Accuracy describes the system’s capacity to correctly identify the
underlying intent despite linguistic variations, paraphrasing, constraints, or
user corrections during an ongoing conversation. Standard statistical metrics
used to evaluate classification performance include:
• Accuracy, Precision, Recall, and F1-Score: Classic classification metrics
evaluating correct vs. misclassified intents across test datasets [8].
• Intent Drift: The phenomenon where user intent shifts over multi-turn
interactions or where external domain changes cause inputs to deviate
from predefined intent boundaries over time [9].
multi-turn intent classification: Multi-Turn Intent Classification
(MTIC) is the task of identifying the intent I of the final user query qn from
a predefined set of possible intents I , given a sequence of user queries in a
chatbot session:
Q = {qi }in=1 .
The prediction of the final intent relies on the conversational context formed
by all preceding user queries:
C = {qi }in=−11 ,
where C represents the historical dialogue context available before the
final query qn . Formally, the objective of MTIC is to learn a mapping function:

f ( Q) = f (C, qn ) → I,

I ∈ I.

Unlike single-turn intent classification, MTIC requires models to interpret
the evolving conversational dynamics and infer user intentions that may

2.2.1

LLM Fundamentals & In-Context Learning

Modern LLMs exhibit strong task performance through In-Context Learning.
This allows them to follow instructions provided directly in the prompt without modifying underlying model weights.
2.2.2

Model Adaptation

When base models require specialization for specific domain tasks or strict
behavioral alignment, model adaptation techniques are applied:
• Full Fine-Tuning: Updating model parameters on task-specific datasets
[13].
• Parameter-Efficient Fine-Tuning (PEFT): Adapting models while keeping the majority of base weights frozen [13].
• Low-Ranked Adaptation (LoRA): Injecting trainable rank-decomposition
matrices into transformer layers to reduce computation [13, 14].
• Prompt-Tuning: Optimizing soft prompt vectors prepended to input
embeddings while keeping model weights fixed [13].
• Prompt Engineering: Optimizing the input prompt in a structured way
to leads a Model to a certain task [13].
2.2.3

Prompt Engineering Techniques & Patterns

A prompt is a set of instructions or information provided to an LLM to
guide its output. It acts as the input on which the model makes predictions and generates responses. Prompt-based learning is the paradigm of
instructing a model to perform specific downstream tasks by leveraging its
pre-trained knowledge through contextual inputs, rather than modifying its

6

2.3 llm security & behavioral steering

core weights via traditional fine-tuning. All other mentioned model adaption
(PEFT, LoRA) needs a re-training in model weights.
Prompt engineering refers to the process of designing, creating, and refining textual inputs (prompts) that are processed by a Large Language Model.
These prompts are intended to instruct the model to perform specific tasks
or generate targeted responses. The quality and structure of a prompt can
significantly influence the output of an LLM. Therefore, effective prompt engineering is essential for obtaining accurate, relevant, and reliable results
from language models [15].

Common prompt strategies include:
• Zero-Shot Prompting: Give an instruction to the model on how to
answer or solve a problem, without any specific example [15, 16].
• One-Shot Prompting: Provide an instruction alongside a single demonstration example [15, 16].
• Few-Shot Prompting: Provide an instruction alongside a few examples
to demonstrate expected behavior [15, 16].
• Prompt Design Patterns: Structured templates and techniques (e.g.,
persona adoption, output format constraints, or Chain-of-Thought reasoning) [15, 16].
2.3

llm security & behavioral steering

Deploying LLMs in production environments introduces behavioral risks that
necessitate dedicated runtime control mechanisms.
2.3.1

Guardrails & Runtime Validation Mechanisms

Guardrails in LLMs are mechanisms that define how a model should behave
by enforcing constraints on its responses. They help guide the model toward producing appropriate and reliable outputs while preventing it from
responding to malicious or unsafe prompts. Depending on the application,
guardrails can enforce requirements such as avoiding harmful content, adhering to predefined conversation flows, maintaining a specific writing style,
or generating structured outputs. These mechanisms can be implemented using techniques such as model alignment during training, prompt engineering, chain-of-thought (CoT) prompting, or external dialogue management
systems. [17]
guardrail techniques: A range of techniques exist for steering the
behavior of large language models. These include model-level adaptation
methods such as fine-tuning, as well as runtime control mechanisms like

7

2.4 agent-based simulation & llm-as-a-judge

prompting and input/output validation. The input/output validation can
be executed by a specific trained LLM or through CoT in the same model.
Validation methods typically operate at three levels:
• Pre- / Post-Validation: Validating inputs before model processing and
filtering outputs before sending them to the user.
• Prompting: Guiding safety bounds directly via system prompts.
• Fine-Tuning: Retraining the base model on curated safety datasets so
it naturally learns to follow safety rules.
2.3.2

Adversarial Vulnerabilities (Prompt Injection & Jailbreaks)

Prompt injection is a technique in which adversarial inputs are used to manipulate an LLM into generating unintended or disallowed outputs, including the disclosure of restricted information or violations of intended behavioral constraints. Jailbreaking represents a specialized form of prompt injection where inputs are structured to systematically bypass safety alignments
and behavioral rules.
agent-based simulation & llm-as-a-judge

2.4

Automated dialogue system testing relies on simulating realistic customer
interactions and evaluating system behavior at scale.
2.4.1

User Simulation Paradigms in Task-Oriented Dialogue

User simulators emulate customer behavior during multi-turn testing:
• Statistical Simulators: Traditional approaches used statistical models
(e.g., Agenda-Based User Simulators) to evaluate dialogue act perplexity and interaction flows [18].
• LLM-Based User Simulators: Modern simulators construct user agents
using LLMs assigned specific personas, goals, and constraints [19, 20].
Evaluation metrics include Task Success Rate, dialogue length, and language diversity.
2.4.2

Qualitative & Quantitative Evaluation via LLM-as-a-Judge

The meaning of LLM-as-a-Judge comes from the usage of the LLM. Through
prompting the model will be forced to "judge" or critic an answer from an
LLM before. Most it is used to just rate an answer to a scale (e.g., from 0 to
10) or to categorize it, like a classifier. For example if an answer is too rude
or contains sensitive information or exhibits hallucinations. [21].

2.5 security & quality assessment frameworks

2.5

security & quality assessment frameworks

Standardized risk-scoring methodologies and threat taxonomies provide objective criteria for evaluating system resilience, quantifying vulnerability severity, and guiding security mitigation strategies in conversational AI systems.
2.5.1

Common Vulnerability Scoring System (CVSS)

The Common Vulnerability Scoring System (Common Vulnerability Scoring System (CVSS)) provides standardized severity metrics to categorize dialogue failure outcomes and security breaches into distinct risk tiers. Within
automated testing frameworks for dialogue systems, CVSS severity scales
range from Informational and Low severity tiers (e.g., minor functional errors or brief fallback loops) up to High and Critical severity levels (e.g.,
system prompt leakage, unverified tool execution, or successful security bypasses)[22].
2.5.2

OWASP Top 10 for Large Language Model Applications

To make evaluation logs structured and actionable for developers and security auditors, failed or degraded dialogues are mapped to standard industry threat taxonomies such as the OWASP Top 10 for Large Language Model
Applications. This mapping allows testing systems to explicitly categorize
specific vulnerabilities identified by evaluator models—such as Prompt Injection (LLM01), Sensitive Information Disclosure (LLM02), System Prompt
Leakage (LLM07), or Excessive Agency and correlate them directly with their
corresponding CVSS risk severity levels.[23]

3.2

llm-as-a-judge

Powerful LLMs (like GPT5, Claude, Gemini 3) have a high similarity in case
of judge a conversation like human preferences over 80% [21]. Which leads to
a good method to approximate human evaluations. The advantage of using
an LLM is the scalability and the low-cost factor in comparison to humans.
Large Language Models (LLMs) can be utilized as judges in two primary
ways. The first is the quantitative approach, which prompts the model to
provide a simple numerical score. A new way is to use them as qualitative
judges that generate structured reports identifying common issue types. Currently, these LLM-generated reports align with manual human annotations
in two out of three cases, serving as a valuable resource to assist developers
during the bug-fixing process. [24]
Except the advantages of LLM-Judges there are limitations which should
also be highlighted. LLM-Judges are vulnerable to biases. Like positional
bias which means a preference for an answer at first or last place in the
prompt. Additionally, the verbosity bias which is the preference for longer
and more detailed answers. [21]. A study highlighted the phenomena Situational Preference that modern LLMs (GPT-4 or Gemini 2.5 Pro) have a
judgment inconsistency of 25% in more complex cases. Beside this is recommended to use deep reasoning or panel-based judges to have a more
consistency. But the inconsistency of LLMs reflect the human annotations,
because they also often inconsistent. [25]
3.2.1

Limitations in Multi-Turn and Sequential Dialogue Evaluation

While single-turn LLM evaluation is thoroughly researched, assessing multiturn conversations introduces distinct challenges that degrade judge reliability:
1. Error Propagation: If an LLM-as-a-Judge misinterprets a user’s intent
in turn n, all subsequent evaluations for turns n + 1 to n + x are based
on a false premise. The state tracking of the judge itself becomes corrupted.

2. Context Inflation and Recency Bias: As the dialogue grows, the input context for the judge increases. Modern LLMs exhibit an "In-theMiddle"-weakness, forgetting details in long contexts, or over-indexing
the very last turn while ignoring the history.
3. Contextual Mildness (Lenient Biases): LLM judges tend to evaluate
later conversational failures more mildly if the initial turns of the dialogue were polite or successful, masking systemic NLU degradation.

llm-agents as simulated user

In context of task-oriented conversations it is possible to use LLMs to simulate a User. But a human user and LLM agentic user distinct in the solution
findings. A human tends to break a problem in multiple steps. (Step-by-step
strategy). LLM Agents lead more likely to an All-in-One Strategy and give
all Information in the first round. [26]

CONCEPT OF THE LLM-BASED TESTING SYSTEM

In this chapter, we present a comprehensive description of the core concept of the LLM-based testing system designed for virtual assistants and
voice bots. In Section 4.1, we present the structured procedure for evaluating LLM-based synthetic data generation against human baselines in a
single-turn setup. In Section 4.2, we adapt this methodology to multi-turn dialogue scenarios and introduce our dual-layer JudgeLLM evaluation engine.
Section 4.3 details our systematic data generation strategies across linguistic variances, out-of-domain boundary defense, adversarial security attacks,
and simulated speech pipeline degradations (STT/TTS). Finally, Section 4.4
formalizes our automated risk scoring and threat mapping framework using
CVSS and Open Worldwide Application Security Project (OWASP) standards.
4.1

single turn intent recognition

In single-turn intent recognition, we evaluate the capacity of large language
models to generate high-quality synthetic utterances that match the distributions of human-crafted benchmark datasets. We evaluate our method on the
BANKING77 dataset, introduced by Casanueva et al. [27], which consists of
13,083 customer service utterances annotated with 77 banking intent classes.
For our evaluation we use the test split dataset with 40 utterances each intent class on different AI models as a baseline. We evaluate our methodology
across three locally hosted open-source models GPT-OSS (120B)[28] , Phi-4
(14B)[29], Mistral-Small (24B)[30] and two commercial cloud models Gemini
3.5 Flash[31] and ChatGPT 5.4 Nano[32]. We use the dataset and evaluate
the quality of classification on the foundation models and afterward synthesize two different AI generated datasets based on the sematic meaning
from the labels with the same 77 banking intents, to compare the ability of
classification. We hypothesize that if a classifier achieves comparable intent
classification accuracy on synthetic data versus human-annotated data under identical prompting conditions, the synthetic dataset adequately mirrors

4.2

multi turn intent recognition evaluation

Evaluating multi-turn conversational NLU systems against human performance is challenging because effective dialogue requires contextually appropriate responses rather than fixed outputs, and internal system access varies.
To address this, we introduce an evaluation framework that combines deterministic statistical metrics with qualitative LLM-as-a-Judge ratings across
three visibility levels.

4.2.1

System Visibility Paradigms

The evaluation framework adapts to the level of internal state access provided by the target architecture:
• White-Box Testing: The framework maintains full visibility into the
target system’s internal classification state, including the top-N intent
candidate distribution, raw confidence scores, and threshold evaluation logic.
• Grey-Box Testing: Access is restricted to external REST API payloads.
The target system returns its spoken text response alongside its top
predicted intent label, concealing internal confidence metrics and secondary hypothesis lists.
• Black-Box Testing: The target system acts as a closed endpoint, returning strictly the spoken text response without intermediate intent
predictions or confidence metrics.

• Definition-Augmented Prompting (Business Logic Injection): The simulator system prompt is injected with explicit intent and domain definitions and explicit negative constraints derived from vector-space sibling clusters. By defining clear semantic boundaries between neighboring intents, this grounding mechanism prevents the simulator from
introducing out-of-scope details.
To systematically measure and mitigate semantic drift within intent clusters, the test generation engine operates across two distinct prompting paradigms:
• Zero-Shot Prompting (Baseline): The simulator receives strictly the

• Definition-Augmented Prompting (Business Logic Injection): In addition to the target label and sibling list, the simulator prompt is augmented with explicit business logic definitions and representative example utterances for both the target intent and all sibling intents in
the cluster. By providing concrete semantic definitions and negative
boundaries, this grounding mechanism grounds the generator and prevents the simulator from introducing out-of-scope details.

automated risk scoring and vulnerability mapping

Every completed dialogue in the testing framework is automatically persisted and evaluated by a dedicated JudgeLLM. To provide actionable feedback to system developers and security auditors, an automated evaluation
pipeline processes the dialogue logs and maps identified issues to standardized risk and security frameworks. Specifically, the framework incorporates
the CVSS for qualitative vulnerability severity scoring, alongside the OWASP
Top 10 for LLM Applications taxonomy to highlight specific threat categories
to the end user.
4.4.1

Standardized Risk Scoring via CVSS

While functional criteria (e.g., intent recognition accuracy or conversation
turn efficiency) assess conversational performance, security and stability issues are categorized according to standardized severity metrics. We adopt
the severity scale defined by the CVSS v3.1/v4.0 specification, which categorizes dialogue outcomes into five risk levels based on their operational and
security impact:
• None / Informational (CVSS 0.0): The dialogue completed successfully without functional or security defects. Minor stylistic deviations
or non-critical persona drifts are logged for prompt tuning.
• Low Severity (CVSS 0.1 – 3.9): The assistant exhibited minor functional errors, such as brief fallback loops or domain boundary leaks on
non-malicious queries, without violating safety constraints.
• Medium Severity (CVSS 4.0 – 6.9): The system experienced moderate logical failures, hallucinated non-critical domain information, or
yielded to non-malicious prompt injections (e.g., abandoning the banking persona to discuss off-topic themes).
• High Severity (CVSS 7.0 – 8.9): A significant vulnerability was exploited, such as System Prompt Leakage (exposing system instructions
or backend configuration details) or executing unverified user-driven
actions.
• Critical Severity (CVSS 9.0 – 10.0): A complete security bypass occurred, including successful jailbreaks, execution of malicious commands, generation of toxic content, or exposure of Personally Identifiable Information.

7

impact of dataset label errors on baseline performance

A notable empirical finding in our single-turn experiments (Section 6.1) is
that all evaluated models achieved consistently higher classification scores
on synthetic persona data (Dsynthetic ) compared to the human baseline (Dhuman ),
yielding a Macro-F1 score gap of ∆ F1 ∈ [−0.0711, −0.0451].
While this delta can be partially attributed to the higher syntactic coherence of LLM-generated text, we hypothesize that a significant portion of this
performance gap stems from inherent label noise within the human benchmark dataset itself.
This hypothesis is strongly supported by recent dataset auditing literature.
Specifically, Ying and Thomas [39] conducted an automated error detection
analysis on the Banking77 dataset, discovering that over 1,400 utterances (≈
14%) in the dataset were mislabelled or ambiguously categorized by human
annotators. In their experiments, removing or correcting these mislabelled
utterances yielded an immediate boost of 4.5% in F1 -score for supervised
classification models [39].
When contextualized against our results, this literature finding provides a
compelling explanation for the performance delta:
1. Annotation Consistency in Synthetic Generation: When an LLM synthesizes test utterances under a target intent prompt (e.g., top_up_reverted),
the generated queries strictly align with the target intent’s semantic
boundary. Synthetic data is therefore virtually free from the mislabeling and cross-intent noise present in human-annotated datasets.
2. Noise Penalization on Human Data: When evaluating intent classifiers against Dhuman , correct predictions are frequently penalized as
False Positives or False Negatives due to ground-truth label errors in
the benchmark test split.
Consequently, we hypothesize that the ∼ 4.5%–7.1% lower performance
observed on Dhuman does not necessarily indicate a lack of diversity in synthetic data, but rather reflects the upper performance ceiling imposed by
noisy human labels in legacy NLU benchmarks. Validating this hypothesis
directly via manual re-annotation of the Banking77 test split remains an
important avenue for future research.
The intra-label vector-space evaluation further substantiates the hypothesis that synthetic datasets effectively bypass the human label noise inherent in the original Banking77 benchmark. As demonstrated in Section 6.1.1,
when utterances are synthesized by a highly capable model like GPT-OSS120B, they remain strictly aligned with the semantic boundaries of the target

7.1 impact of dataset label errors on baseline performance

intent (Thematic Accuracy: 0.91). Crucially, although the model exhibits a
linguistic diversity comparable to human language (Diversity Score: 1.10),
the synthetic data points position themselves precisely around the correct
intent centroid without overlapping into adjacent classes. This supports the
assertion that synthetic generation via LLM prompting filters out the crossintent noise and mislabeling artifacts present in the estimated 14% of flawed
human annotations [39]. Ultimately, the synthetic dataset preserves the necessary formulation variance required for robust NLU testing while eliminating the artificial error ceiling imposed by legacy human label errors.
